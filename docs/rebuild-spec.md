# Casa Artis Calendar v2: rebuild specification

**Status:** ready to build · **Date:** 24 Sep 2026 · **Owner:** Alex Radu
**Source:** the v1 app in this repository. It is an approved working mockup: the features and flows are approved; the code and visual design are not.
**Audience:** a coding agent (or developer) building v2 from scratch, in a new folder, without reusing v1 code.

---

## 0. How to use this document

- **What v2 must do.** Everything in §3–§7 describes required behaviour. When this spec and v1 disagree, follow the spec: many v1 behaviours are listed on purpose as bugs to fix (§15).
- **How to build it.** §8–§13 set the data model, API, stack, security, design system and quality bar. Library choices are decisions, not suggestions. Deviate only if a library is broken, and say why in the pull request.
- **v1 as a reference.** Run v1 (`npm start`, then sign in as `demo_admin` / `demo123`) to see an approved flow. Never copy its markup, CSS or JS.
- **Language.** The UI is in **Romanian first, English second**. Romanian labels are given in quotes with their English meaning, e.g. "Programează" (Schedule).
- **Build order.** Work milestone by milestone (§16). Every milestone ends green: its tests pass, and nothing from an earlier milestone breaks.
- **Wording.** "Must" means required. "Should" means expected unless there is a good reason. "May" means optional.

### Non-goals for v2

The following are out of scope: native mobile apps; installing as an app (PWA); offline editing; publishing directly to social networks through their APIs; payments or ticketing; a public-facing site for attendees; multiple organisations (one install serves one organisation); a real-time collaboration UI (optimistic concurrency is enough).

## 1. Product overview

Casa Artis is a cultural venue with event rooms (**spaces**) and guest accommodation (**rooms**). The app has three parts:

1. **Team events calendar**, for every signed-in user. It holds three kinds of entries:
   - public events (workshops, masterclasses);
   - blocked time slots (maintenance, private use);
   - room-only bookings (guests and trainers staying overnight).

   Users schedule entries through a guided form that shows availability, warns about conflicts and suggests free alternatives.
2. **Social media planner**, for admins only. It is a content calendar of posts per platform (TikTok, Instagram, Facebook, YouTube, Reddit, and custom ones), with each platform's current size and format standards built in. A **promotion queue** turns new public events into social posts.
3. **Administration**, for admins only. It covers users, spaces, rooms, all events, and storage (usage against a configurable cap, plus cleanup tools).

**Demo mode.** Two public demo accounts let prospects try the app on a sandbox copy of the sample data. The sandbox is reset nightly and on every restart.

## 3. Roles and permissions

### 3.1 Roles

| Role | Who |
|---|---|
| `user` | Team member or mentor who schedules their own entries |
| `moderator` | Staff member who also manages guest accommodation |
| `admin` | Full access |

**Demo flag.** `is_demo` is a flag on an account, not a role. Demo accounts work only on the demo workspace (§4.7).

**Root admin.** The first admin created at install is the **root admin**. It cannot be deleted, demoted or renamed. The root admin can hand over root status to another admin; this is new in v2.

### 3.2 Permission matrix (enforced on the server; the UI only mirrors it)

| Action | user | moderator | admin |
|---|:-:|:-:|:-:|
| View the team calendar (all entries) | ✓ | ✓ | ✓ |
| See private notes of blocked slots | own only | ✓ | ✓ |
| Create public events and blocked slots | ✓ | ✓ | ✓ |
| Edit or delete an entry | own only | own only | any |
| Create room-only bookings; add or change room bookings on any entry | ✗ | ✓ | ✓ |
| Reassign an entry to another user | ✗ | ✗ | ✓ |
| Social planner (view and edit) | ✗ | ✗ | ✓ |
| Admin panel: users, spaces, rooms, storage, all-events audit | ✗ | ✗ | ✓ |
| Manage own passkeys and own password | ✓ | ✓ | ✓ |

**Demo accounts** follow the same matrix, but only inside the demo workspace. They can never create or change users, passkeys, passwords or settings.

**Ownership.** An entry belongs to `owner_id`, a user id and nothing else. It is never matched by username.

## 4. Functional specification: platform

### 4.1 Sign-in

**Login screen**

- A centred card with the app name, a language switch (RO/EN) and a theme switch.
- Fields: "Nume utilizator" (Username) and "Parolă" (Password), plus a show/hide password button.
- "Autentificare" (Sign in) button.
- "sau" (or) divider, then a "Autentificare cu cheie de acces" (Sign in with passkey) button. Show it only when the browser supports WebAuthn in a secure context.
- A "Ați uitat parola?" (Forgot password?) link.
- Demo accounts:
  - When enabled, show two chips: "Demo Utilizator" and "Demo Administrator".
  - Each chip signs in through a dedicated endpoint, `POST /api/auth/demo {account}`. It does not fill in a password, so it keeps working when the demo password is changed.
  - Hide the chips entirely when demo accounts are disabled.
- Errors are **translated** and generic: "Nume de utilizator sau parolă greșită" (wrong username or password). Never reveal whether a username exists.

**Password sign-in**

- Usernames are case-insensitive and are not trimmed on the server; the client trims them.
- Passwords are never trimmed anywhere.

**Passkey sign-in**

- Username-less: uses a discoverable credential.
- User verification is required.
- The origin must be in `APP_ORIGINS`.

**After sign-in, go to:**

1. the page the user tried to open, if their role allows it; otherwise
2. their last visited page (saved per browser); otherwise
3. the Events calendar (for admins as well).

**Sign-out**

- "Deconectare" (Sign out) deletes the server session.
- A "Deconectează toate sesiunile" (Sign out everywhere) action is available in account settings.

### 4.2 Accounts, invitations and password reset (new)

**Invitations** (admin → new user)

1. The admin enters the name, username, email and role.
2. The server creates the user with **no password** and sends an invitation email containing a single-use link: `/invite/<token>`, valid for 72 h.
3. The invitee opens the link, chooses a password (policy in §11.2) and may add a passkey straight away.
4. **If email is not configured** (no SMTP), the admin sees the link with a "Copiază linkul" (Copy link) button instead. The admin can also always resend the invitation or copy a fresh link.

**Forgot password**

1. From the login screen the user enters their username or email.
2. The server **always** replies with the same message: "Dacă există un cont, veți primi un email" (If an account exists, you'll get an email).
3. The reset link is single-use and valid for 60 min.
4. Completing a reset revokes every session of that user.

**Admin reset.** An admin can trigger "Trimite link de resetare" (Send reset link), or copy the link. Admins **never** see or set another user's password directly.

**Account settings** (for every user; opened from the user menu)

- Name, email and theme preference.
- "Schimbă parola" (Change password): requires the current password.
- Passkeys: list them, add one (optional name), rename, remove.
- "Sesiuni active" (Active sessions): device and browser, last seen, and a revoke button for each.

**Tokens**

- Invitation and reset tokens are 32 random bytes, sent base64url-encoded.
- Only a **SHA-256 hash** of a token is stored.
- Tokens are single-use, and are consumed atomically.

### 4.3 App shell and navigation

**Desktop (> 900 px)**

A top bar containing, from left to right:

- the logo or app name;
- the tabs "Calendar", "Programează" (Schedule), "Evenimentele mele" (My events, with a count badge), and "Social" (admins only);
- on the right: the "Admin" link (admins only; it shows a warning dot when storage is at 80% or more), then the user menu. The user menu shows the avatar and name and holds: Account settings, Passkeys, Language, Theme and Sign out.

**Tablet and phone (≤ 900 px)**

- A **bottom tab bar**: Calendar, Programează, Ale mele (Mine), Social (admins only), and "Mai mult" (More).
- The tab bar respects the safe-area insets.
- "Mai mult" opens a bottom sheet with: the user's name and role, Admin (admins only), Account settings, Language, Theme and Sign out.
- The top bar shows only the page title and one contextual action.

**Routing**

- Real URLs using the History API, e.g.:
  - `/calendar?view=month&date=2026-09`
  - `/schedule`
  - `/my-events`
  - `/social?view=feed&month=2026-09&platform=instagram`
  - `/admin/users`
  - `/entries/:id` (the detail view)
- A reload restores exactly the same view.
- The Back button works.
- Deep links work.

**Preferences**

- Theme: `system` (the default, following `prefers-color-scheme`), `light` or `dark`. Saved to the account when signed in; kept in localStorage before sign-in.
- Language: saved the same way, defaulting to Romanian.
- UI state (last calendar zoom, platform filter, admin tab): saved in localStorage.

**Staying fresh**

- When the tab regains focus (throttled to at most once per 30 s), and every 5 min while visible, refetch the data for the visible range.
- Saves use optimistic concurrency (§9.1). On `409 conflict`, show a message: "Acest element a fost modificat de altcineva" (This item was changed by someone else), reload the item, and keep the user's unsaved input in the form so nothing typed is lost.

**Feedback**

- Toasts: info, success, warning and danger. They appear bottom-right on desktop and above the tab bar on phones, sit in an `aria-live` region, and auto-dismiss after 5 s; danger toasts stay until dismissed.
- Every successful save shows a success toast.
- Confirmation dialogs always have an explicit **Cancel** that aborts. Destructive choices never hide behind "Cancel" (see the recurrence scopes in §5.5).
- Loading states use skeletons. An empty state always has one sentence of explanation and one primary action.

### 4.4 Internationalisation

- All UI text lives in translation files: `/app/i18n/ro.json` and `/app/i18n/en.json`, with the same keys in both.
- Messages use ICU MessageFormat (plurals: RO has one/few/other, EN has one/other). Use the browser's `Intl.PluralRules` together with a small formatter; no heavy i18n library is needed.
- Dates, times, numbers and currency are formatted with `Intl` in the UI locale: `ro-RO` or `en-GB`.
- Week starts on Monday; times use the 24-hour clock.
- Server error responses carry a stable `code`. The client translates the code and never shows raw server text.
- Seed and sample content comes in Romanian. Platform-standards text may stay in English, since those are industry terms.
- A test fails the build when keys are missing, unused or duplicated (§13).

### 4.5 Time zone

- One organisation time zone, set in settings. The default is `Europe/Bucharest`.
- All calendar logic works in that zone, whatever the browser's zone is.
- The database stores local date and time strings, plus UTC instants where an exact moment matters (sessions, tokens, audit).
- "Today", "past" and "current hour" are always computed in the organisation zone. v1 mixed UTC and local time; that bug must not return.

### 4.6 Media and uploads

**Accepted files**

| Kind | Formats | Size limit |
|---|---|---|
| Images | JPEG, PNG, WebP, GIF, AVIF | up to `MAX_UPLOAD_MB` (default 100 MB) |
| Videos | MP4, MOV, WebM | up to `MAX_UPLOAD_MB` (default 100 MB) |

- File type is detected from the file's content (magic bytes). The extension and the declared type are ignored. SVG, HTML and anything else is rejected.

**Upload flow**

- Files are sent directly (`POST` with the raw body). The client uses `XMLHttpRequest`, because `fetch` has no upload progress, and shows a progress bar.
- The original filename goes in `X-Filename`, percent-encoded so that Romanian diacritics survive.
- The server **streams** the body to a temporary file while hashing it, and never buffers the whole upload in memory.
- Several files can be selected at once. Each file becomes one media record.

**Processing on the server** (with `sharp` for images; `ffprobe-static` and `ffmpeg-static` for video, both optional dependencies that are detected at runtime)

- **Images:**
  - Read width and height.
  - Strip EXIF (privacy: removes GPS data).
  - Generate a **WebP thumbnail** 480 px wide.
  - Keep the original.
- **Videos:**
  - Read width, height, duration and codec.
  - Generate a poster frame as a WebP thumbnail.
  - If `ffmpeg` is not available, skip the video metadata and show "—" in the UI.

**Media record**

- Fields: `id`, `sha256` (identical files are stored once), `original_name` (shown in the library, editor and post detail), `mime`, `bytes`, `thumb_bytes`, `width`, `height`, `duration_s`, `thumb_path`, `created_at`.
- Who uploaded a file is tracked in `media_owners` (media id, user id, created at). With deduplication, one file can have several uploaders, and "my uploads" in the library uses this table.
- Records link to the entries and posts that use them through join tables (§8), not by searching text.

**Serving**

- Files are served at `/media/:id/:variant` (`original` | `thumb`).
- Access requires being signed in to the same workspace. Demo media is visible only to demo sessions.
- Headers: `Cache-Control: private, max-age=31536000, immutable` (URLs are content-addressed) and `X-Content-Type-Options: nosniff`.
- Always sent with an explicit `Content-Type`, and `Content-Disposition: inline`.

**Cleanup**

- Media nothing references is deleted by a job every hour, once it is older than 24 h. The grace period allows for unsaved forms.
- Removing media from a post or entry makes it unreferenced right away. The file itself goes at the next job run.

**External links**

- Posts and covers may use an external `https://` URL instead of an upload.
- The UI shows a preview. Metadata (size) is read in the browser where possible.

### 4.7 Demo workspace

- A **workspace** is a complete, separate dataset: its own SQLite file and its own media folder. There are two:
  - `main`, the real data;
  - `demo`, the sandbox.
- Demo accounts (`demo`, a user; `demo_admin`, an admin) authenticate against the main user table. Their sessions are bound to the `demo` workspace.
- **Isolation:** demo sessions can never read or write main-workspace data, and the other way round.
- **Reset:** the demo workspace is rebuilt from the seed on every server start and daily at `DEMO_RESET_HOUR` (default 03:00, organisation time zone). The reset uses a real scheduler; don't use an hourly polling approximation.
- **Limits** (because the demo password is public):
  - storage cap `DEMO_STORAGE_CAP_MB` (default 200);
  - upload rate limit of 20 files per 10 min **per IP**, because demo accounts are shared;
  - no email sending.
- **User lists:** inside the demo, only the demo accounts and fictitious seed users are visible. Real users are never visible.
- **Banner:** a thin banner at the top of the page: "Mod demonstrativ — datele se resetează zilnic" (Demo mode: data resets daily).
- **Switching off** (`ENABLE_DEMO_ACCOUNTS=0`) disables the demo accounts and hides the demo chips. Existing demo sessions are revoked.

## 5. Functional specification: team events calendar

### 5.1 Entry model (a clean redesign of v1)

Every calendar item is an **entry**. The common fields and the per-type fields are listed below.

**Common fields**

| Field | Notes |
|---|---|
| `id` | UUIDv7, generated by the server |
| `type` | `event` \| `blocked` \| `room_only` |
| `title` | 1–120 characters, required |
| `description` | Markdown-lite: line breaks and links only, rendered safely |
| `owner_id` | The user who owns the entry |
| `series_id` | null, or the series it belongs to (§5.5) |
| `sessions[]` | 1–60 sessions for `event` and `blocked`; none for `room_only`. Each has `date` (YYYY-MM-DD), `start` (HH:MM) and `end` (HH:MM). `end` > `start` on the same day. `end` may be `24:00` to mean midnight; sessions never cross midnight. Multi-day entries use several sessions or the room-booking dates |
| `room_bookings[]` | Staff only. Each has `room_id`, `check_in` (date), `check_out` (date, strictly after `check_in`), `guests` (integer ≥ 1) and `guest_names` (optional) |
| `version` | Integer, for optimistic concurrency |
| `created_at`, `created_by`, `updated_at`, `updated_by` | Audit fields |

**Type `event` (public event)**

| Field | Notes |
|---|---|
| `space_id` | Required |
| `price` | Either free (`price_cents` null) or an amount: `price_cents` (integer) plus `currency` (`RON` \| `EUR`). Plus an optional `price_note` (e.g. "reducere studenți", student discount) |
| `enroll_url` | Required, `https://` only |
| `cover_media_id` or `cover_url` | Required. Must be 16:9 (§5.6) |
| `promotion_status` | `pending` \| `promoted` \| `skipped`. Derived from the linked posts (§6.7), but `skipped` is set manually |

**Type `blocked` (blocked slot)**

| Field | Notes |
|---|---|
| `space_id` | Optional. Null means "whole venue / no specific space" |
| `description` | Private: shown only to the owner and staff (§3.2) |

**Type `room_only` (room booking)**

| Field | Notes |
|---|---|
| `sessions` | Empty |
| `room_bookings` | At least one row. The entry's date range is derived from them |

**Sessions**

The session model replaces three separate v1 concepts:

- "consecutive hours": one session;
- "separate hours": several sessions on the same date;
- multi-day events: several sessions on different dates.

Each session has an explicit end time. There is no `hour` plus `duration` pair, and no `scheduledHours`.

### 5.2 Calendar views ("Calendar")

**Header**

- The period label, `‹` and `›`, and "Astăzi" (Today).
- A segmented control for the view: "An" (Year), "Lună" (Month), "Săptămână" (Week, desktop only), "Zi" (Day) and "Listă" (Agenda).
- A **filter** button that opens a popover with:
  - entry type (event / blocked / room booking), multi-select;
  - space, multi-select;
  - owner: all, mine, or a specific user. Each option shows its entry count for the visible period.

  Filters are shown as removable chips under the header and are stored in the URL.
- A **"+ Programează"** (Schedule) button.
- Keyboard shortcuts on desktop: `t` today; `←`/`→` previous/next; `y`/`m`/`w`/`d`/`l` switch view; `n` new entry.

**Year view**

- Twelve mini-months, with Monday-first weekday initials.
- Each month shows its entry count. The count includes entries that **span** the month, not only those that start or end in it.
- Marking:
  - days with entries get a dot, colour-coded by type (max 3 dots);
  - today is marked;
  - past days are dimmed.
- Hovering a day (desktop) shows a tooltip listing the entries. Clicking a day opens the **Day** view for that date. Clicking a month title opens that month.

**Month view**

- A 6-row, Monday-first grid. Weekend columns are tinted. Days from the adjacent months are dimmed.
- **Desktop:** each day shows up to 3 entry chips (time, a type icon and the title, in the owner's colour), then "+N mai multe" (+N more), which opens a day popover.
  - Clicking the empty area of a day, or its day number, opens the Day view.
  - A "+" appears on hover over today and future days.
- **Phone:** the grid is compact, with coloured bars (max 3 per day). Tapping a day opens a **bottom sheet** with that day's agenda and a "+ Programează în această zi" (Schedule on this day) button.
- Multi-day entries show on every day they cover.

**Week view (desktop)**

- Seven columns with a time axis. The default visible hours are 08:00–22:00, with a toggle for 00:00–24:00; the toggle choice is remembered.
- A "now" line on today.
- **Overlapping sessions are laid out side by side** in columns (v1 stacked them on top of each other).
- Each session block shows its time range, title, type icon, owner chip and space.
- **Clicking an empty slot** starts a new entry, prefilled with that date and time.
- **Drag to create** (optional, "may"): dragging across empty slots selects a time range.

**Day view**

- The same as the Week view, but one column. This is the default on phones.
- On phones, swipe left and right to change day, and `‹`/`›` move one day.

**Agenda view ("Listă")**

- A chronological list of sessions grouped by date, starting from today, with infinite scroll forward.
- A "Afișează trecutul" (Show past) toggle.
- Best for phones and for searching.

**Search.** A search field, available in all views, filters by title, description, space, room, owner and guest names. In non-agenda views, matches are highlighted and everything else is dimmed.

**Colours**

- Entries use the **owner's colour** (from their user profile; admins can edit it).
- The type is shown by an **icon and pattern**, not by colour alone:
  - blocked slots: a diagonal hatch and a lock icon;
  - room bookings: a bed icon.
- There are no hard-coded usernames or colours (v1 had these).

**Past rules**

- Anything before the current moment is "past": dates before today, and today's time before the current hour.
- Past slots cannot be selected to create an entry.
- Past entries can still be opened and **edited by admins only**, and deleted by their owner or an admin. Editing a past entry shows a warning banner.

### 5.3 Scheduling form ("Programează")

The form opens as a page (`/schedule`, and `/entries/:id/edit`) on every screen size. On desktop, a quick-create from the calendar opens the same form as a side panel over the calendar.

v1 used a step-by-step wizard. v2 uses **one scrollable form in sections**:

- a sticky section index on desktop, and collapsible sections on phones;
- a sticky summary and action bar at the bottom;
- sections for a type that doesn't apply are hidden, never merely disabled.

A validation error scrolls to the first invalid field and focuses it. Errors show inline, next to the field.

**Section A: "Tip" (Type)**

- A segmented control: "Eveniment public" (public event), "Blocare interval" (blocked slot), and "Doar cazare" (room booking, shown for staff only).
- Changing the type keeps every field that still applies.

**Section B: "Detalii" (Details)**

| Field | Types | Rules |
|---|---|---|
| Titlu (title) | all | Required. The label adapts per type: "Titlu eveniment", "Motiv blocare" (reason for the block), "Nume rezervare / oaspeți" (booking / guest names) |
| Spațiu (space) | event (required), blocked (optional) | Select of **enabled** spaces showing "Name · capacity". The capacity is a number stored as `capacity_people` and displayed as "80 locuri" (80 seats) |
| Descriere (description) | all | Plain-language hint. For blocked slots the label is "Note private" (private notes), with an explanation of who can see them |

**Section C: "Dată și oră" (Date and time)** (event and blocked only)

Three modes:

- "O sesiune" (one session, the default): date, start and end.
  - The end time defaults to start + 2 h.
  - Picking a new start shifts the end by the same amount.
  - A duration display ("2 h 30 min") is shown alongside.
- "Mai multe sesiuni în aceeași zi" (several sessions on the same day): a date, then a list of start–end rows. Rows may not overlap each other.
- "Mai multe zile" (several days): a list of date + start + end rows, with an "adaugă zi" (add day) button. Rows are sorted automatically.

**Availability strip** (next to each session's date)

- One row per hour from 08:00 to 22:00 (the full day when the toggle is on), for the **selected space**. For a blocked slot with no space, the strip covers all spaces.
- Each cell shows one of four states:
  - "Liber" (free): clickable. It sets the start time, and the end time keeps the current duration.
  - "Ocupat" (busy): the tooltip names the conflicting entry and its owner.
  - "Trecut" (past): disabled.
  - "Selectat" (selected): the current session.

**Conflicts and suggestions** are in §5.4.

**Section D: "Recurență" (Recurrence)** (event and blocked; not available in several-days mode)

See §5.5.

**Section E: "Cazare" (Accommodation)** (staff only; required for room bookings, optional for events)

- For events, a "Necesită cazare" (Needs accommodation) switch reveals the section. Room bookings always show it.
- Each booking row has:
  - room: select of **enabled** rooms, showing "Name · type · capacity";
  - check-in and check-out: check-out must be after check-in (hotel semantics: check-out day = free for a new check-in);
  - guests: a number, at most the room's capacity; above that, show a warning that doesn't block saving;
  - guest names: optional.
- "+ Adaugă cameră" (Add room) adds a row. Removing the last row, when the entry is a room booking, is prevented with a hint.
- New rows default to the event's first session date (for events) or to today (for room bookings). Dates are computed in the organisation time zone.
- Room conflicts are **blocking** (§5.4).

**Section F: "Publicare" (Publishing)** (event only)

- Preț (price): a "Gratuit" (free) toggle, **or** an amount with a currency select (RON/EUR), plus an optional price note.
- Link înscriere (enrolment link): required, and must be a valid `https://` URL.
- Copertă (cover image): see §5.6.

**Summary bar** (sticky)

- A one-line summary, e.g. "Eveniment public · Sala Mare · joi 1 oct, 18:00–20:00 · 3 sesiuni lunare" (public event · main hall · Thu 1 Oct, 18:00–20:00 · 3 monthly sessions).
- Buttons: "Anulează" (Cancel), then the primary save button, whose label adapts:
  - "Salvează evenimentul" (save event)
  - "Confirmă blocarea" (confirm block)
  - "Salvează rezervarea" (save booking)
- Leaving the page with unsaved changes asks for confirmation.
- Drafts are autosaved to localStorage, per user, and restored on return with a "Draft restaurat" (draft restored) notice and a "Renunță" (Discard) link.

**Defaults when opening**

- From a calendar date or slot, that date and time.
- Otherwise the **next full hour, today**, rolling to tomorrow at 09:00 when later than 21:00. v1 defaulted to the 15th of the viewed month, which was often in the past.

### 5.4 Availability, conflicts and suggestions

**Busy time.** A space is busy for time T when any `event` or `blocked` entry in that space has a session that covers T. For a blocked slot with no space, **every** space is busy for that time. Room bookings never make a space busy.

**Space conflict rules** (new in v2; v1 only warned)

| New entry | Overlaps | Result |
|---|---|---|
| event | another event in the same space | **Blocked.** Error listing the conflicting entry. Admins can tick "Permite suprapunerea" (Allow overlap), which asks for confirmation and is recorded |
| any | a blocked slot | **Blocked** (that is the purpose of a blocked slot). Admins can override as above |
| blocked slot | an existing event | **Blocked**, with the same admin override |

**Room conflict rule.** A room cannot have two bookings whose `[check_in, check_out)` ranges overlap. This is always blocked, with no override. The check covers bookings within the same form, which v1 did not check.

**Enforcement.** The server enforces every conflict rule inside the write transaction and returns `409 conflict` with `details` listing each conflicting entry (`id`, `title`, `owner`, time). The client runs the same checks live, as the user edits, so the user sees problems before saving.

**Conflict panel.** When there is a conflict, an inline panel appears next to the date and time section (not at the top of the page), with:

- the conflicting entries, as links that open in a popover;
- up to 3 suggestions, each with a "Folosește" (Use) button:
  1. "Prima oră liberă în aceeași zi" (first free hour on the same day): the first slot of the same duration, at or after 08:00, that is free, not past, and ends by 22:00.
  2. "Aceeași oră, următoarea zi liberă" (same time, next free day): the same time on the next day, within 30 days, where that time range is free. This is a real availability check, not "a day with no entries at all" as in v1.
  3. "Aceeași zi, săptămâna viitoare" (same day, next week): +7 days, if free.

  Using a suggestion updates the session and re-runs the checks. It **never** jumps to a past time.
- A calm, non-blocking **info** note when other entries exist that day in *other* spaces (e.g. "Alte 2 evenimente în acea zi", 2 other events that day), so users still get v1's awareness without an alarm.

### 5.5 Recurrence

**Rule.** "Se repetă" (Repeats) offers:

| Option | Meaning |
|---|---|
| Nu (the default) | No repetition |
| Săptămânal (weekly) | Every N weeks, on chosen weekdays |
| Lunar – aceeași zi (monthly, same day) | e.g. the 15th. Short months use their last day |
| Lunar – aceeași zi a săptămânii (monthly, same weekday) | e.g. the 3rd Thursday |

The end is either "după N apariții" (after N occurrences, 2–52) or "până la data" (until a date, at most 12 months ahead).

**Preview.** A live preview lists the dates, e.g. "6 sesiuni: 1 oct, 5 nov, 3 dec, … 4 mar". Occurrences that would conflict are marked with a warning icon. The user can **skip individual dates** by clicking them.

**Conflicts in a series.** Saving a series that still contains a conflicting occurrence fails as a whole with `space_conflict` or `room_conflict`, listing the dates. The user must skip those dates, or an admin can override space conflicts (§5.4). Room conflicts can't be overridden.

**Storage**

- A `series` row holds the rule, the start and the end.
- Each occurrence is materialised as its own entry, with `series_id` and an `occurrence_index`.
- Skipped dates are stored as exceptions.
- Room bookings on a recurring event are **shifted** per occurrence: each occurrence gets bookings relative to its own date, and every booking is conflict-checked. (v1 copied the same dates to every occurrence.)

**Edit and delete scope.** Editing or deleting an entry that belongs to a series asks with three explicit radio options plus a real Cancel:

- "Doar această sesiune" (only this one): detaches the entry and marks the date as an exception.
- "Aceasta și următoarele" (this and following): splits the series at this date; earlier sessions are untouched.
- "Toată seria" (the whole series): applies to every occurrence **that is not in the past**. Past occurrences are never changed or deleted by a series operation.

The operation is atomic: all occurrences change, or none do.

### 5.6 Cover image (public events)

**Sources**

- Upload a file (§4.6).
- Paste an `https://` URL.
- Pick an image from the media library: the admin's previous uploads, shown as a grid of thumbnails.

**Validation**

- Width/height must be between **1.70 and 1.85** (16:9 is 1.78).
- Recommended minimum size: 1200×675. Smaller images get a warning but can still be used.
- The result is shown with a preview and a badge:
  - valid: "1920 × 1080 · 16:9" (green);
  - wrong shape: shown in red, e.g. "Pătrat" (square), "Portret" (portrait), "Banner ultra-lat" (ultra-wide banner), or the ratio;
  - the image failed to load: a red error.
- Save is blocked only while the entry type is `event` and the cover is invalid. Switching to another type clears the block (v1 left the save button disabled after a type switch).

**Crop helper (new, "should").** When the image is not 16:9, offer "Decupează la 16:9" (crop to 16:9): a simple draggable 16:9 frame over the image. The crop is done on the server with sharp and saved as a new media file.

**Sample image.** In the demo workspace only, a "Folosește imagine exemplu" (use sample image) button fills in a sample 16:9 cover.

### 5.7 Entry detail

**Where it opens**

- Desktop: a side panel.
- Phones: a full-screen sheet.
- Every entry also has its own URL, `/entries/:id`.

**Contents**

- The cover image, for public events.
- The type badge, title and owner (avatar and name).
- Sessions, e.g. "joi, 1 oct 2026 · 18:00–20:00", listed one per line when there are several.
- The space, with capacity.
- Room bookings, e.g. "Camera 1 · 1–3 oct · 2 oaspeți" (Room 1 · 1–3 Oct · 2 guests), for staff and the owner.
- The price, e.g. "Gratuit" (Free) or "75 RON · reducere studenți" (75 RON · student discount).
- The enrolment link, as a button.
- The description. For blocked slots it is visible only to those allowed; everyone else sees "Note private".
- The series, e.g. "Seria: lunar, 3 din 6" (Series: monthly, 3 of 6), with a link to see all occurrences.
- The promotion status, for admins: "De promovat" (to promote), "Promovat" (promoted, with links to the posts) or "Ignorat" (skipped).

**Actions** (only those the user is allowed):

- "Editează" (Edit)
- "Duplică" (Duplicate): opens the form prefilled, dated to the next free slot.
- "Șterge" (Delete): scoped for series.
- "Promovează" (Promote): admins, public events only; opens the post editor prefilled (§6.7).
- "Reatribuie" (Reassign): admins only; pick a new owner.

Users without edit rights see a subtle "Doar vizualizare — creat de {name}" (View only, created by {name}).

### 5.8 My entries ("Evenimentele mele")

- Entries the user owns, grouped into "Următoare" (upcoming, the default) and "Trecute" (past, collapsed), each sorted by date.
- Filter tabs: "Toate" (All), "Evenimente" (Events), "Blocări" (Blocks) and, for staff, "Cazări" (Bookings). Each tab shows a count. A search box filters the list.
- Each card shows: the type badge, next session date and time, title, space and rooms, price (events), a status line (promotion status for events, visible to admins), and actions: Edit, Details, Duplicate and Delete.
- The nav badge counts only **upcoming** owned entries.
- Empty states, one for "nothing yet" and one for "no match":
  - "Nu aveți încă nimic programat" (You have nothing scheduled yet), with a "Programează" (Schedule) button;
  - "Niciun rezultat pentru filtrele alese" (No results for the chosen filters), with a "Resetează filtrele" (Reset filters) button.

### 6.3 Post editor

**Where it opens**

- Desktop: a side panel.
- Phones: a full-screen sheet.

**Fields**

1. **Platformă** (platform): shows enabled platforms. When editing, a disabled platform the post already uses also appears, labelled "(dezactivată)" (disabled).
2. **Format.**
3. **Standards card**: a live summary of the selected format (ratio, resolution, file formats, duration, file size, caption limit, hook length and safe zone). It can be collapsed.
4. **Dată și oră publicare** (publish date and time): defaults to the next full hour.
5. **Titlu** (title): internal, required.
6. **Media**
   - Drag & drop, a file picker, a URL, or picking from the media library.

- If that fails, show a coloured circle with the platform's initial.

### 6.7 Promotion queue ("Coadă promovare")

**Which events appear**

- Upcoming public events (`type = event`, next session today or later) with `promotion_status = pending`.
- Blocked slots and room bookings **never** appear.
- Past events are excluded from the counts.

**Badge.** Shows the number of pending upcoming events.

**Filters**

- "De promovat" (To promote): pending. This is the default.
- "Promovate" (Promoted): has at least one linked post.
- "Ignorate" (Skipped).
- "Toate" (All).

The filters must actually work; in v1 every filter showed "all".

**List.** Sorted by next session, soonest first. Each card shows:

- the cover thumbnail and title;
- the next session date/time, space and owner;
- the price;
- the linked posts (as chips with the platform icon);
- actions:
  - "Creează postare" (Create post);
  - "Ignoră" (Skip), and "Anulează ignorarea" (Undo skip).

**Create post from an event**

Opens the post editor prefilled with:

- **Platform:** the last platform used for promotion (remembered), otherwise Facebook, otherwise the first enabled platform. The format is the first one matching the cover's 16:9 ratio, otherwise the platform's first format.
- **Date/time:** 7 days before the first session at 10:00. If that is already past, use the next full hour.
- **Title:** "Promovare: {event title}" (Promotion: …).
- **Caption:** built from a **template** that admins can edit under Settings → "Șablon promovare" (Promotion template). The default template:

  ```
  🚀 {title}
  Susținut de {owner}
  📅 {date}, {time} · {space}
  🎟️ {price}
  🔗 Înscrieri: {enroll_url}

  {description}
  ```

- **Media:** the event cover.
- **Link:** `event_id` is set to the event.

**Status updates**

- Saving the post sets the event's `promotion_status` to `promoted`.
- Deleting the event's last linked post returns the event to `pending`. (v1 left the event marked promoted.)

## 8. Data model (SQLite)

### 8.1 Files, access and conventions

**Files**

- One SQLite file per workspace: `data/main.db` and `data/demo.db`.
- A separate `data/auth.db` holds users, sessions, passkeys and tokens, which are shared by both workspaces.
- Each workspace connection runs `ATTACH 'auth.db' AS auth`, so operations that touch both, such as deleting a user with transfer or searching by owner name, run in **one** `BEGIN IMMEDIATE` transaction.
- SQLite foreign keys can't cross files. References from workspace tables to `auth.users` (`owner_id`, `created_by`, `updated_by`) are therefore enforced in the service layer and covered by tests.

**Access**

- Use Node's built-in `node:sqlite` (`DatabaseSync`). It has no native build step, so it works on Windows and Linux alike.
- `node:sqlite` is a release candidate in current Node docs. Some Node 24 minors may still print an `ExperimentalWarning`; that is acceptable, so filter that one warning out of the logs.
- Pin the Node 24 minor in CI and in `.nvmrc`.
- Keep all database access in a small data layer (`server/db/*.js`). That way `better-sqlite3` can be swapped in if ever needed.
- Pragmas: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`.

**Migrations**

- Numbered SQL files in `server/db/migrations/NNN_name.sql`.
- Applied at startup inside a transaction.
- The current version is recorded in `PRAGMA user_version`.

**Conventions**

| What | Convention |
|---|---|
| Ids | `TEXT` UUIDv7 |
| Timestamps | `TEXT` ISO-8601 UTC, e.g. `2026-09-24T10:00:00Z` |
| Local dates | `TEXT` `YYYY-MM-DD` |
| Local times | `TEXT` `HH:MM` |
| Money | `INTEGER` cents |
| Booleans | `INTEGER` 0/1 |

## 9. HTTP API

### 9.1 Conventions

**Base and format**

- The API is served under `/api/v1`. Requests and responses are JSON, except media uploads.
- Every write body is validated with **Zod** schemas that live in `/shared/schemas/*.js`. The browser imports the same files, so client and server validate with one set of rules.
- Unknown fields are rejected.

**Authentication and CSRF**

- A session cookie authenticates each request (§11.3).
- Every mutating request **made with a session** must send an `X-CSRF-Token` header that matches the session's `csrf_token`. The token is returned by `GET /api/v1/session`.
- Requests made before sign-in (login, demo, passkey sign-in, forgot, token) have no session yet. They are protected by the Origin check (§11.4) and by rate limits.

**Optimistic concurrency**

- Every resource returns `version`, and its `ETag` is `W/"<version>"`.
- `PATCH`/`PUT`/`DELETE` must send `If-Match`.
- If the version doesn't match, the server returns `409 {error:{code:"version_conflict", details:{current}}}`.

**Errors**

- Shape: `{ "error": { "code": "snake_case", "message": "dev-facing English", "details": {…} } }`.
- The UI translates `code`.
- Status codes:

  | Status | Meaning |
  |---|---|
  | 400 | Validation error, with `details.fields` |
  | 401 | Not signed in |
  | 403 | Signed in but not allowed |
  | 404 | Not found |
  | 409 | `version_conflict`, `space_conflict`, `room_conflict` or `in_use` |
  | 413 | Too large |
  | 415 | Unsupported media type |
  | 429 | Rate limited |
  | 507 | `storage_full` |

**Lists**

- Parameters: `?from=&to=` (dates), `?q=`, `?limit=&cursor=`.
- Responses: `{items, nextCursor}`.

**Rate limits**

- Rate limits use SQLite-backed counters (§11.5).

## 10. Technology and architecture

### 10.1 Principles

- **No front-end build step.**
  - The browser loads native ES modules.
  - Libraries come from a CDN through an **import map**, with **exact pinned versions**.
  - There is no bundler, no transpiler and no TypeScript compile step.
  - Types come from JSDoc comments, checked by `tsc --noEmit --allowJs --checkJs` in CI only.
- **Small, fast and dependable**, with these budgets:

  | Budget | Limit |
  |---|---|
  | JS transferred on first load | ≤ 120 KB gzip, including libraries |
  | LCP on a mid-range phone over 4G | < 2 s |
  | API p95 on a small VPS | < 100 ms |
- **One process, one SQLite file per workspace, one media folder.** Deployable to any small VPS or Windows PC with Node 24.
- **The server is the source of truth.** Every rule in this spec is enforced on the server. The client repeats checks only for instant feedback.

### 10.2 Front end

**Libraries** (loaded through the import map in `public/index.html`)

- `?external=preact` keeps a single Preact instance across all packages.
- **CDN URLs.** Pin the build target too: add `&target=es2022` (or `?target=es2022`) to every esm.sh URL. esm.sh answers bare package URLs with small stubs that re-import target-specific files, and the target can change with the User-Agent.
- **Self-host option.** `npm run vendor`:
  1. installs the same exact versions as devDependencies;
  2. copies their ESM builds from `node_modules` into `public/vendor/`;
  3. writes `importmap.local.json`.

  The server serves that map when `ASSETS=local`, for offline or locked-down installs; the default is `cdn`. The CSP (§11.6) allows only the CDN host that is in use.
- **Integrity.** Subresource integrity is required only for `ASSETS=local`, where the files are fixed. There, hash the vendored files in CI.
- **Types.** The same packages are exact-pinned **devDependencies**, so `tsc --checkJs` can resolve types. A CI check keeps their versions identical to the import map.

**Rules**

- Don't use a calendar library. The views in §5.2 are specific and must stay light, so build them as custom components on CSS Grid. This gives full control of design, phones and performance. FullCalendar was considered and rejected: it is heavy, needs a paid licence for resource views, and is hard to restyle.
- Don't use a CSS framework or Tailwind. Use hand-written modern CSS (§12).
- Icons: **Lucide**, as an inline SVG sprite generated once by a script (`npm run icons`) from `lucide-static@1.47.0` and saved as `public/icons.svg`. Use only the icons the app needs, and don't fetch icons at runtime. A custom bed icon may be added where Lucide has none.
- Font: **Inter Variable**, self-hosted as a woff2 from `@fontsource-variable/inter@5.3.0` (copied by the vendor script). Use `font-display: swap`, and fall back to the system UI font.

## 11. Security requirements

### 11.1 Threat model (short)

- The app faces the internet and has a public demo login.
- Its users are a small team.
- The assets to protect are the team's accounts, the schedule and guest names (personal data under GDPR), and the media.

### 11.2 Passwords

**Hashing**

- Use **argon2id** with memory 64 MiB, 3 iterations and parallelism 1. Benchmark at startup: if one hash takes more than 500 ms, log a warning.
- Store the hash in PHC string format.
- After a successful login, **rehash** the password if the stored parameters are older than the current ones.

**Policy** (NIST SP 800-63B)

- Length: at least **12** characters, at most **128**. Count Unicode code points.
- No rules requiring particular kinds of characters.
- The password must not equal, or contain, the username, the email local part, or the app name.
- Reject the **10,000 most common passwords**, using a list bundled in `server/auth/common-passwords.txt`.
- Breach check (optional, **on by default** when outbound network is available): query the Have I Been Pwned k-anonymity API. Only the first 5 characters of the SHA-1 hash are sent. If the service is unreachable, allow the password (fail open).
- The UI shows a strength meter and the specific reason a password was rejected. Show/hide buttons appear on every password field.

**Rules**

- Never trim passwords.
- Never log them.
- Never send them back to the browser.
- There are no hardcoded or default passwords anywhere, including the demo: demo accounts have no usable password and can sign in only through `/auth/demo`.

**Login defences**

- If the user doesn't exist, still verify against a dummy hash, so the response takes the same time.
- Increasing delay per username+IP: after 5 failures within 15 minutes, wait 30 s, doubling each time up to 15 min.
- An IP limit on top of that: 30 attempts per 15 minutes.
- Only **failed** attempts count.
- Honour `TRUST_PROXY` when working out the client IP.

**Migrating from v1:** see §14.

### 11.3 Sessions

**Cookie**

- An opaque random value (32 bytes) in a cookie named `__Host-sid`, with `HttpOnly; Secure; SameSite=Lax; Path=/`. In development over plain http the cookie is named `sid` and is not `Secure`.
- The server stores only the SHA-256 of the cookie value, never the value itself.
- No JWT. v1 used a JWT with a version number to revoke sessions; server-side sessions make revocation, listing and idle timeouts straightforward.

**Lifetime**

- The session ID is rotated on login and whenever privileges change.
- Idle timeout: `SESSION_IDLE_HOURS`. Absolute lifetime: `SESSION_TTL_DAYS`.

**Revocation.** All of a user's sessions are revoked when:

- their password is changed or reset;
- their role is changed;
- their account is disabled;
- they choose "sign out everywhere";
- an admin revokes them.

Expired sessions are pruned by a job every hour.

### 11.4 CSRF and CORS

**CSRF**

- The session's token must be sent in the `X-CSRF-Token` header on every mutating request made with a session. Requests made before sign-in are exempt (see §9.1).
- **In addition**, check the `Origin` (or `Referer`) header against `APP_URL`.

**CORS.** Disabled: the app is same-origin only.

### 11.5 Rate limiting

Counters are stored in SQLite (`rate_limits`).

| Area | Limit |
|---|---|
| Login | See §11.2 |
| Forgot password | 5 per hour per IP; 3 per hour per account |
| Passkey sign-in | Treated like login |
| Demo sign-in | 30 per hour per IP |
| Uploads | 60 per 10 min per user in main; 20 per 10 min **per IP** in the demo |
| Every other write | 300 per 5 min per user |

### 11.6 HTTP headers and CSP

**Content-Security-Policy**

- `default-src 'self'`
- `script-src 'self' 'sha256-<hash of the import map>' https://esm.sh`. With `ASSETS=local` there is no CDN host.
  - An import map must be an **inline** `<script type="importmap">`; browsers don't load it from `src`.
  - At startup the server builds `index.html` for the active `ASSETS` mode, computes the SHA-256 of the import map, and adds it to `script-src`.
  - No other inline script is allowed.
- `style-src 'self'`
- `img-src 'self' blob: data: https:`. `https:` is needed for external post media and covers.
- `media-src 'self' blob: https:`
- `font-src 'self'`
- `connect-src 'self' https://esm.sh`
- `object-src 'none'`
- `base-uri 'none'`
- `frame-ancestors 'none'`
- `form-action 'self'`

**No `'unsafe-inline'` anywhere.**

- Dynamic styles must be set through the CSSOM (`el.style.setProperty`, which Preact uses) or through CSS custom properties. Never use inline `style=` in server HTML.
- v1 needed `unsafe-inline` for styles; v2 must not.

**Other headers**

- `Strict-Transport-Security: max-age=31536000; includeSubDomains`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Resource-Policy: same-origin`
- `X-Content-Type-Options: nosniff`

### 11.7 Input and output

- Every input goes through Zod: exact types, length limits, enums and date formats.
- URLs (`enroll_url`, `share_link`, external media) must be `https:`.
  - `share_link` may also be a UNC path matching `^\\\\[^\\/:*?"<>|]+\\…`.
  - `javascript:` and `data:` are always rejected.
- Descriptions and captions are rendered as text. The only formatting allowed is:
  - line breaks;
  - `https` links, which are auto-linked with `rel="noopener noreferrer" target="_blank"`.
- No `innerHTML` with any data. Preact escapes values by default; `dangerouslySetInnerHTML` is forbidden, and a lint rule enforces this.
- CSV export guards against formula injection: any cell starting with `= + - @` gets a leading `'`.

### 11.8 Privacy (GDPR, basic)

**Personal data.** Guest names and user emails are personal data.

**Controls**

- Admins can export and delete any user's data.
- Guest names can be cleared from past bookings by the storage cleanup ("Șterge numele oaspeților mai vechi de N zile", delete guest names older than N days).
- The app sets no cookies other than the session cookie, and does no tracking.

**Logs**

- Pino logs are structured, with request id, user id, route, status and duration.
- Secrets and personal data are redacted from logs.

### 11.9 Supply chain

- Pin exact versions of all server dependencies, with `package-lock.json` committed.
- Run `npm audit --omit=dev` in CI.
- Front-end CDN versions are pinned in the import map, with the vendor option and hash check described in §10.2.

## 12. Design system and UX

Aim: a **calm, professional, venue-appropriate** interface.

**Keep from v1**
- The dark and light themes.
- The clear information hierarchy.

**Fix from v1**
- Visual noise: glows, gradients on everything, and 7 different tab styles.
- Inconsistent components.
- The light theme was a patch layer over the dark one.

**Both themes are designed together, from the same tokens.**

### 12.1 CSS architecture

**Layers.** `@layer reset, tokens, base, layout, components, utilities;` Specificity is controlled by the layers, so there is **no `!important`** (lint rule).

**Modern CSS to use:**
- native nesting;
- `:has()`;
- container queries, so components adapt to their container rather than the viewport;
- `color-mix()`;
- `light-dark()` combined with `color-scheme`;
- logical properties;
- `dvh` units;
- `@starting-style` for dialog and sheet entry animations.

**Tokens.** Every value comes from a custom property; no raw hex values appear in component CSS.

- **Colour:** OKLCH primitives, then semantic tokens:
  - surfaces: `--surface-0/1/2/3`
  - text: `--text-strong/default/muted/disabled`
  - borders: `--border-subtle/default/strong`
  - accent: `--accent`, `--accent-contrast`
  - status: `--success/--warning/--danger/--info`, each with `-bg` and `-fg` variants
  - entry types: `--type-event/--type-blocked/--type-room`
  - focus: `--focus-ring`
- **Owner colours:** 12 preset hues (`--owner-1` … `--owner-12`), each checked to reach 3:1 against both surfaces as a bar and 4.5:1 as text on a tinted chip. Users pick from these presets only.
- **Brand accent:** one accent hue. **Proposed:** a deep teal, `oklch(55% 0.09 200)`. This is an open decision for the owner (§17).
- **Spacing:** a 4-px scale, `--space-1` (4 px) up to `--space-12` (48 px).
- **Type:** Inter, with the scale 12 / 13 / 14 / 16 / 18 / 20 / 24 / 30 px (`--text-xs` … `--text-3xl`). Body text is 14 px on desktop and 16 px on phones, so iOS doesn't zoom into inputs. Use tabular numbers (`font-variant-numeric: tabular-nums`) in calendars and tables.
- **Radius:** 6 / 10 / 14 / 20 px, plus pill.
- **Elevation:** 3 shadows, which are subtle in light mode and become border and surface steps in dark mode.
- **Motion:** 120 / 200 / 320 ms, easing `cubic-bezier(.2,.8,.2,1)`. Everything is disabled under reduced motion.
- **Breakpoints:** 640 px (phone) and 900 px (tablet). Prefer container queries inside components.

**Themes.** `:root { color-scheme: light dark }`, following the system by default. `[data-theme=light|dark]` overrides it. Both themes must pass the contrast checks.

### 12.2 Components (one of each, with documented states)

**Consolidation (v1 → v2)**
- **Segmented control:** used for view switches and entry type. It replaces v1's 7 tab and segmented variants.
- **Tabs:** for page sections and filters, with an optional count badge.
- **Badge:** neutral, accent, success, warning, danger and type variants. It replaces v1's 22 badge classes.
- **Chip:** filters and entry chips in the calendar. It can be removed, selected, and carry an owner colour.

**Every component has the states:** default, hover, active, focus-visible, disabled, loading and error, wherever each applies.

**Full component list:**
- Buttons: primary, secondary, ghost, danger; sizes sm, md, lg; icon-only (always with `aria-label`).
- Inputs: text, textarea, select (native `<select>`, styled), date, time, number, colour preset picker, switch, checkbox, radio group, search field with clear.
- Field wrapper: label, hint, error, required marker, character counter.
- Dialog (desktop, centred), Sheet (phone bottom sheet, draggable handle), Side panel (desktop detail and edit), Popover.
- Toast, inline Alert (info, warning, danger), Banner (demo, storage).
- Data table that switches to cards on phones through container queries (driven by the component itself; no `MutationObserver` hack).
- Avatar (initials plus owner colour), EmptyState, Skeleton, Progress bar, Meter (storage).
- Calendar primitives: DayCell, SessionBlock, AvailabilityStrip, MiniMonth.

### 12.3 Layout and page patterns

- **App frame**
  - Desktop: top bar, then content with a max width of 1280 px, centred.
  - Detail and edit views open in a side panel 440–520 px wide, so the calendar stays visible behind them.
- **Phone frame:** compact top bar, content, bottom tab bar. Sheets are used for detail and quick actions; the form is full-screen.

  - Today gets an accent ring.

- **Empty and loading states** everywhere, as in §4.3.

## 14. Migrating data from v1

Provide `npm run import-v1 -- --users <users.json> --workspace <data/workspace.json> --uploads <data/uploads>`. It imports into a **fresh** v2 main workspace, runs as a single transaction, and has a `--dry-run` mode that prints a report.

**Mappings**

| v1 | v2 |
|---|---|
| user `{id, username, name, role, color, isDemo, passwordHash (bcrypt)}` | `users`. Keep the ids in a lookup map; v2 creates new UUIDs. Colours map to the nearest owner preset. `is_demo` users are skipped. Existing users become `active` |
| bcrypt `passwordHash` | Store it with the prefix `legacy-bcrypt:`. On the first successful login, verify it with `bcryptjs`, then **rehash to argon2id** immediately. After 90 days, show admins a list of accounts that never logged in, so they can send them reset links |
| passkeys (passwordless-id format) | **Not migrated.** The stored key formats differ. The import report lists the users who had passkeys, and they re-register after their first password login. An in-app banner invites them to |
| event `{startDate, endDate, hour, durationHours}` | One entry. It gets one session per day from `startDate` to `endDate`, each at `hour` → `hour + duration` |
| v1 event whose `hour + duration` crosses midnight | Split into a session until `24:00` and one from `00:00` the next day |
| event `scheduledHours[]` (separate hours) | One session per listed hour, each 60 min long |
| `entryType` `event` / `locked` / `room_only` | `event` / `blocked` / `room_only` |
| `roomBookings[{roomId,startDate,endDate}]` | `room_bookings` with `check_in = startDate` and `check_out = endDate + 1 day` (v1 dates were inclusive), `guests = 1` |
| legacy `roomId` | One booking covering the event's date range, converted the same way |
| free-text `price` + `currency` | If it parses as a number (ignoring `$`, `€`, `lei`, `RON`, spaces), store `price_cents` and the currency, using the symbol to decide the currency. Values such as "Free…" or "Gratuit" become free. Anything else goes to `price_note` |
| event `location` (free text, seed only) | Appended to `description` as "Locație: …" (Location: …) |
| `facebookImage` `/uploads/x` | Import the file as media and set `cover_media_id` |
| `facebookImage` external URL | `cover_url` |
| `isRecurrent`, `recurrenceGroupId`, `recurrenceIndex`, `recurrenceTotal` | A `series` row with a monthly rule (`count = recurrenceTotal`), linked to each entry |
| `socialStatus` | `pending` / `promoted` stay the same. `none` becomes null |
| `promotedPostId` | Sets `posts.event_id` on that post |
| `creatorId` | `owner_id`, through the user map. Unknown creators go to the root admin, with `owner_name_snapshot = creatorName` |
| spaces `{name, capacity:"80 persoane", color, description, enabled}` | `capacity_people` is the integer parsed from the text |
| rooms `{name, type, capacity:"2 oaspeți", beds, color, notes, enabled}` | `capacity_guests` is the parsed integer; `beds` stays text |
| platform + `postTypes[]` | `platforms` + `formats`. Parse ratio text like `9:16`. Durations are free text in v1: parse numbers where possible and put the rest in `safe_zone`/notes |
| post `{date, time, title, description, status, mediaUrl, mediaCount, mediaType, shareLink}` | `posts` with `caption = description`. Media is imported as for covers. `mediaCount > 1` with only one URL becomes a single media item |

**Report.** At the end the script prints counts, skipped items and warnings (unparseable prices, missing files, orphaned owners).

## 15. v1 defects not to carry over

This list comes from auditing v1. Each item is already covered by the spec above; it is repeated here so that none of these behaviours comes back by accident.

**Events**
1. Space overlaps were never blocked, and blocked slots didn't actually block anything.
2. Editing a multi-day event collapsed it to one day.
3. A "whole series" edit regenerated the series from the edited date and deleted earlier sessions. Cancel on the series prompts meant "only this one", so there was no real cancel.
4. Recurring events with rooms copied the same room dates to every occurrence.
5. Room check-out and check-in on the same day counted as a conflict.
6. Room rows within one form weren't checked against each other.
7. A room-only entry's date span came from a hidden field.
8. Room-only entries had a fake 18:00–20:00 time.
9. Blocked slots couldn't have notes, because that step was never reached.
10. The save button stayed disabled after switching type away from an invalid cover.
11. The default date was the 15th of the viewed month, often in the past.
12. Suggestions could propose past hours. "Next free day" meant "a day with no entries at all".
13. Timeline cards overlapped instead of sitting side by side. There was no "now" line.
14. Yearly counts missed events that spanned the month.
15. The user filter bar was never visible.
16. Entry colours were hard-coded by username.
17. The server checked ownership by id while the client checked it by username.
18. Room bookings counts ignored `roomBookings`.
19. Dates were computed in UTC in some places.

**Social**
1. Search missed captions and formats.
2. The promotion filters all showed "all".
3. Blocked slots, room bookings and past events were counted as "to promote".
4. Media wasn't validated against the format, despite UI text saying it was. Only the first selected file was uploaded, and media couldn't be removed.
5. Deleting a post left its event marked promoted.
6. Deleting a platform left orphaned posts.
7. "Reset to defaults" wiped all posts.
8. Import had no validation or preview.
9. Most format fields weren't editable, and a browser `prompt()` was used to add formats.
10. Duplicating a post could land it in the past.
11. The default time was inconsistent: 12:00 in some places, 09:00 in others.

**Platform and security**
1. JWT sessions with manual version bumps.
2. Synchronous bcrypt; passwords trimmed inconsistently.
3. The password policy allowed only 10 characters with no blocklist.
4. A hard-coded demo password lived in the login markup, and demo chips showed even when demo was disabled.
5. Uploads were served without authentication.
6. An unescaped `href` in the admin table (possible `javascript:` URLs).
7. No server-side schema validation; owners could forge `creatorName` and `socialStatus`.
8. One shared rate limiter that also counted successful logins, and no `trust proxy`.
9. The test reset endpoint had no authentication.
10. A deleted user's events were orphaned, and reusing that username linked the new user to them.
11. The whole dataset lived in one JSON file rewritten on every save, with last-write-wins and no conflict detection.
12. `style-src 'unsafe-inline'` was needed because of inline style toggles.
13. The "All" category badge was hard-coded, and the storage badge showed the cap instead of usage.
14. A non-admin reaching an admin page was sent to login.
15. Server errors were shown untranslated.
16. The theme ignored the system preference.
